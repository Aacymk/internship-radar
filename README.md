# Internship Radar

**Tells you the day an internship application opens.**

Internship applications open on no announced schedule. Miss the week a posting
goes up at a company you cared about and, for large programs, that is the
cycle. The usual workaround is checking twenty careers pages by hand, which
is time ineffective

Aggregating job postings is the easy half of that problem. The hard half is
that a tracker which re-reports the same posting every morning trains you to
ignore it — and then you miss the one that mattered. So this tracks **change**,
not inventory: a posting is reported exactly once, the first time it appears,
and is remembered from then on.

## Set it up (no coding required)

### 1. Make your own copy

Click **Use this template** → **Create a new repository** at the top of this
page. Give it a name. Leave it public or make it private — both work.

> Everything from here happens in **your** copy, not this one.

### 2. Choose your companies

Click `config.yml` in your new repository, then the **pencil icon** to edit it.

Add or remove company names under `companies:`. Each one goes on its own line
beginning with two spaces and `- `:

```yaml
companies:
  - Netflix
  - Databricks
  - Rivian
```

Update `season:` to the cycle you are targeting:

```yaml
season: "Summer 2027"
```

Click **Commit changes** at the bottom when you are done.

> **The one thing that trips people up:** the indentation has to be exactly
> two spaces before each `- `. If you get it wrong the tracker will stop and
> tell you which line to fix, so nothing silently breaks.

### 3. Turn it on

Open the **Actions** tab and click the green button to enable workflows.

Then choose **Check for new internship postings** from the sidebar and click
**Run workflow**. The first run records everything currently open as your
starting point without alerting you — otherwise your first notification would
be several hundred jobs that opened months ago.

### 4. Make sure it can reach you

Open **Settings** → **Actions** → **General**, scroll to **Workflow
permissions**, and select **Read and write permissions**. This lets it save
results and post notifications. Click **Save**.

That is the whole setup. From now on it checks every morning on its own.

## Architecture

One run is a straight pipeline: **fetch → normalize → dedup → diff against
history → report → remember.**

`sources/` fetches. Every source — a company's ATS or a community list — is
just something that produces `Listing`s ([`sources/base.py`](radar/sources/base.py)).
The runner doesn't know or care which kind it's talking to; ~35 of them run
concurrently under one pooled HTTP client.

`model.py` normalizes. Two functions decide identity: `canonical_url` strips
tracking params so the same posting from four lists collapses to one, and
`normalize_company` matches "JPMorganChase" to "JP Morgan Chase". Everything
downstream trusts these keys.

`state.py` remembers. `data/state.json` is the only memory between runs — a
map of canonical URL to the date it was first seen. A run's job is to diff
today's listings against it, not to re-derive history.

`report.py` and `cli.py` are the only parts that know a human is involved:
building the GitHub issue body and rewriting the README table. Nothing above
them touches formatting.

The dependency direction is one-way — `sources` knows nothing about `report`,
`model` knows nothing about either. That's what let concurrency get bolted
onto `sources/base.py` later ([Design notes](#design-notes)) without anything
else in the pipeline changing.

## Design notes

Four decisions carry most of the weight.

**Novelty is the alert gate, not content filters.** It would be easy to filter
postings by role title or season and only alert on "real" matches. That trades
a false positive — a listing you glance at and dismiss in two seconds — for a
false negative, a posting you never hear about at all. Those costs are not
symmetric, and only one of them is recoverable. So nothing is filtered out on
suspicion of being irrelevant; the only gate is whether the posting is new.

**Identity is the canonical URL, not the raw one.** Job lists append tracking
parameters (`?utm_source=...`) that differ between lists and change over time.
Keying on the raw URL means the same job counts as several postings, and one
list changing its link format re-alerts you about everything at once. Stripping
them ([`model.py`](radar/model.py)) also collapses the same posting reported by
four different lists into one row.

**The first run alerts on nothing.** Adopting a season already in progress
means several hundred long-open postings are "new" to an empty state file.
Reporting them would bury the signal on day one, so the first run records the
baseline silently ([`state.py`](radar/state.py)).

**Sources are fetched concurrently, but reassembled in configured order.** A
run is ~32 sources of almost pure network wait, none of which depend on each
other, so they go out together rather than one at a time
([`sources/base.py`](radar/sources/base.py)). A full run went from ~22s to
~4.5s, in two separate steps worth separating: sharing one pooled HTTP client
across every source (so repeat calls to the same host reuse the connection)
took it to ~15.6s, and fetching concurrently took that to ~4.2s.

The interesting half is not the speed. Deduplication keeps the *first*
listing seen for a URL, so if results were processed as they arrived, the
source credited for a posting would depend on which server happened to answer
first, and `state.json` would churn with diffs that mean nothing. Results are
therefore gathered concurrently but reassembled in configured order, which
keeps the output identical to the sequential version — same 1093 postings,
same attribution, every run.

Two bounds keep that fast path honest. Concurrency is capped at 10 requests
in flight, because these are free public APIs and unbounded parallelism is a
good way to get blocked from them. And each source gets a wall-clock deadline,
because fetching concurrently means a run is only as fast as its *slowest*
source: one board timing out slowly was turning a 4s run into an 80s one.
Dropping that source costs one board's postings for a day; not dropping it
costs the entire run's latency.

The season matcher is worth a look too: `season_pair` requires the season and
year to be adjacent with no digits between them, which is what separates a
*Summer 2027 internship* from a *Summer 2026 internship for 2027 graduates* —
the single most expensive mistake this kind of tool makes.

## Testing philosophy

Tests are weighted toward where a wrong guess is expensive and silent, not
toward coverage percentage.

**Parsing gets the most scrutiny.** `test_joblists.py` and `test_sources.py`
exist because a community list's README is a moving target — column order,
markdown vs. HTML tables, missing links — and a parser that silently returns
zero rows on a format change is worse than one that crashes, because nothing
tells you the tracker went blind. Robustness cases (`TestRobustness`,
`TestHtmlTables`) lock in "parse what you can, skip what you can't" rather
than "never fail."

**Identity and novelty are tested in isolation from I/O.** `TestCanonicalUrl`,
`TestNormalizeCompany`, and `TestNovelty` don't touch the network — getting
these wrong doesn't crash the run, it corrupts it quietly, either by
re-alerting on old postings or merging two different jobs into one.

**Concurrency is tested for the property that matters, not the mechanism.**
`TestDeterminism` in `test_sources.py` doesn't check that fetches happen in
parallel — it checks that the *output* doesn't change when they do, which is
the actual guarantee the [Design notes](#design-notes) concurrency section
depends on. `TestFailureIsolation` and `TestSourceDeadline` cover the other
half: one bad source shouldn't take down or slow down the rest.


## Running it locally

Not required for normal use.

```bash
pip install -r requirements.txt
python -m radar --dry-run
```

| Flag | Effect |
| --- | --- |
| `--dry-run` | Report findings, write nothing |
| `--baseline` | Record everything as seen, alert on nothing |
| `--digest PATH` | Write the notification body to a file |
| `--config PATH` | Use a different config file |

Exit codes: `0` nothing new, `10` found something new, `1` failed, `2` bad
config. The workflow keys off `10` to decide whether to notify.

```bash
pip install -r requirements-dev.txt
python -m pytest
```

Lint and type checks, both gated in CI:

```bash
ruff check radar tests
mypy radar
```

## Limitations

- **Name matching is exact-ish.** "Meta" will not match a list that writes
  "Meta Platforms, Inc." Normalization handles spacing, case, and punctuation
  only.
- **Community lists can be wrong.** They occasionally carry postings for the
  wrong season or region. This tool surfaces what they publish rather than
  second-guessing it — see the design note above for why.
- **A posting is alerted once.** If a company pulls a posting and reposts it at
  the same URL, that is not new.
- **Scheduled runs are best-effort.** GitHub delays cron jobs under load, and
  disables workflows in repositories with no activity for 60 days.
